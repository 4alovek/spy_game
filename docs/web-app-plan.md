# План: веб-версия игры «Шпион»

Превращаем Telegram-бота в веб-приложение, переиспользуя существующую игровую
логику. Telegram-бот **остаётся** работать параллельно — это просто второй адаптер
над общей логикой.

## Принятые решения

- **Аутентификация:** гости (постоянный ID в `localStorage`) по умолчанию; интерфейс
  `User` закладывается так, чтобы позже добавить Telegram Login Widget без переделок.
- **Фронтенд:** vanilla JS / HTML / CSS, без сборщика.
- **Бот:** остаётся, работает параллельно с вебом поверх той же логики.
- **Бэкенд:** Python (FastAPI + WebSocket) — чтобы переиспользовать `game_logic.py`
  как есть, без переписывания.

## Главная идея

`game_logic.py` уже **чистый** — в нём нет импортов `telegram`. Бот рассылает события
игрокам через `broadcast_to_lobby` (`bot.py`). В вебе тот же приём — это
WebSocket-рассылка. Значит, логику переиспользуем, а Telegram-адаптер заменяем
веб-адаптером.

```
                ┌────────────────────────┐
                │  game/ (чистая логика,  │   ← переиспользуем как есть
                │  без I/O)               │
                └───────────┬────────────┘
            ┌───────────────┼────────────────┐
   adapters/telegram/   adapters/web/    (будущие адаптеры)
       bot.py          FastAPI + WS
```

## Целевая структура проекта

```
spy_game/
  game/            game_logic.py, workplaces.py   # чистая логика (без I/O)
  adapters/
    telegram/      bot.py                          # существующий бот
    web/           app.py, ws_manager.py, protocol.py, routes.py
  persistence/     models.py, repository.py, stats_service.py
  frontend/        index.html, app.js, styles.css
  tests/
```

Импорты в боте и тестах меняются на пакет `game` (например `from game.game_logic
import GameManager`).

## Бэкенд (FastAPI)

- `ConnectionManager` — прямой аналог `broadcast_to_lobby`: хранит
  `{lobby_id: [websockets]}` и рассылает JSON-события всем в лобби вместо
  Telegram-DM.
- REST для входа: `POST /lobby` (создать), `GET /lobby/{id}` (проверить
  существование). Дальше всё взаимодействие — по WebSocket.
- **Протокол событий** (pydantic-схемы):
  - клиент → сервер: `join`, `set_name`, `add_place`, `start`, `stop`, `accuse`,
    `guess`, `vote`, `chat`;
  - сервер → клиенты: `lobby_update`, `role_assigned` (личное), `vote_started`,
    `game_result`, `chat`, `error`.
- **Централизовать завершение раунда.** Сейчас результат определяется в трёх местах
  вразнобой (обвинение и голосование в `button_handler`, плюс ручной `win`). В вебе
  свести в одну функцию `resolve_round(...)`, которая и рассылает результат, и пишет
  статистику. Это единственная точка подключения расширений.

## Расширение 1: БД и статистика побед/поражений

Сейчас всё в памяти и эфемерно (`GameManager` — глобальный объект, перезапуск стирает
всё), у игроков нет постоянной личности — только `user_id`.

**Identity.** Гость: при первом заходе фронт генерирует UUID, кладёт в `localStorage`,
шлёт на бэкенд. `User` создаётся/находится по этому ID. Поле `auth_provider`
(`guest` | `telegram` | ...) оставляет место для Telegram Login позже.

**Схема БД** (SQLAlchemy async, SQLite для dev → Postgres для prod, Alembic для
миграций):

- `users(id, display_name, auth_provider, external_id, created_at)`
- `games(id, lobby_id, workplace, spy_user_id, result, started_at, ended_at)`
- `game_players(game_id, user_id, role, is_winner)`
- `user_stats(user_id, games, wins, losses, times_spy, spy_wins)` —
  материализованная агрегация.

**Сервис статистики.** `StatsService.record_game(...)` вызывается **только** из
`resolve_round`. `game/` про БД ничего не знает — чистота сохраняется. Эндпоинт
`GET /users/{id}/stats` для страницы профиля.

## Расширение 2: текстовый чат

Новый тип сообщения `chat` по тому же WebSocket → `ConnectionManager` транслирует его
в лобби. Опционально — сохранять историю в таблицу `messages`.

## Расширение 3: голосовой чат

- **WebRTC mesh** для небольших групп (≈3–8 игроков — как раз размер партии).
  Бэкенд работает сигнальным сервером по уже существующему WebSocket (обмен
  SDP/ICE), отдельная инфраструктура не нужна.
- При росте числа участников / требований к надёжности — перейти на SFU
  (LiveKit / mediasoup). Начинать с mesh.

## Правки в текущем коде (минимальные)

- Выделить чистую логику в пакет `game/`, адаптеры — в `adapters/`.
- Привести результат игры к единому типу: сейчас методы возвращают то `GameResult`
  (enum), то строки `"workers_win"` / `"spy_win"` — для записи в БД нужен один формат.
- Голосование резолвится только когда проголосовали **все** работники
  (`get_vote_result`) — в вебе добавить таймаут / возможность хоста форсировать.

## Фазы

1. **Паритет с ботом в вебе** — FastAPI + WS + vanilla-фронт, состояние в памяти.
   Та же игра в браузере: лобби, роли, остановка, обвинение, догадка шпиона,
   голосование, результат.
2. **Identity + БД + статистика** — гостевые аккаунты, запись игр, страница профиля.
3. **Текстовый чат** — по WS.
4. **Голосовой чат** — WebRTC mesh + сигналинг.

## Масштабирование (на будущее, не на старте)

Состояние в памяти годится для одного процесса. Для нескольких инстансов лобби нужно
вынести в Redis + pub/sub для рассылки. Делать только когда понадобится.
