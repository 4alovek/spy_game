# Кроссплатформенная игра и VPS-развёртывание

## Summary

Игроки из Telegram и браузера участвуют в одном лобби и одном раунде через единый Python-процесс. Продакшен-запуск — Docker Compose с контейнерами приложения и PostgreSQL; HTTPS пока не настраивается, поэтому WebRTC-голос в VPS-сборке явно отключается/помечается как требующий HTTPS.

## Architecture Decisions

- Общий `GameCoordinator` владеет игровыми сессиями, блокировками лобби, завершением раунда, статистикой и доменными событиями. Веб- и Telegram-адаптеры не имеют собственных `GameManager`.
- ID игроков канонизируются в `web:<guest_uuid>` и `tg:<telegram_id>`; привязки аккаунтов между платформами нет.
- Создание лобби сразу добавляет создателя в список игроков на обеих платформах.
- Веб-участник при обрыве соединения до старта удерживает место 1 минуту; при переподключении таймер отменяется. Telegram-игроки не зависят от WebSocket.
- Первый релиз работает в одном процессе. Координатор получает интерфейсы хранилища и рассылки, чтобы позднее заменить in-memory состояние и события на Redis без переделки адаптеров.
- PostgreSQL — единственная БД Docker-развёртывания; SQLite остаётся допустимым для локальной разработки и тестов. Схема управляется Alembic, а не неявным `create_all` в продакшене.
- Чат и голос не становятся кроссплатформенными: чат остаётся вебовым, голос доступен только при HTTPS.

## Tasks

### T1. Нормализовать игровую модель и идентичность

**Зависимости:** нет.

- Перевести `Player`, `Lobby` и `GameManager` на строковые ID; привести все результаты к `GameResult`, устранив строки вида `workers_win`.
- Добавить модуль канонизации identity: веб принимает только UUID гостя и формирует `web:<uuid>`, Telegram формирует `tg:<id>`.
- Сохранить чистоту пакета `game/`: никаких импортов БД, FastAPI или Telegram.
- Обновить unit-тесты логики для строковых ID и обоих результатов раунда.

**Готово, когда:** ID с разных платформ не пересекаются, а действующие правила игры проходят прежние и новые unit-тесты.

### T2. Реализовать общий координатор игры

**Зависимости:** T1.

- Создать `GameCoordinator` с единственным `GameManager`, `asyncio.Lock` на каждое лобби и операциями: создать, войти, выйти, изменить имя, добавить место, начать, остановить, угадать, обвинить, проголосовать, вручную завершить и закрыть лобби.
- Ввести типизированные доменные события: изменение лобби, старт, остановка, догадка, голосование, итог, отмена и закрытие.
- Сделать единый resolver раунда: снимок результата до сброса ролей, одноразовая запись статистики, публикация итога.
- Определить порты `LobbyStore` и `EventPublisher`; реализовать in-memory варианты для первого релиза.
- Добавить явный выход веб-игрока из лобби и отложенное удаление отключившегося веб-игрока через 1 минуту.

**Готово, когда:** два одновременных действия не могут дважды завершить раунд или создать две записи статистики.

### T3. Перевести веб-адаптер на координатор

**Зависимости:** T2.

- Заменить глобальные `game_manager`, `_handle_action` и `_resolve_round` вызовами `GameCoordinator`.
- Сохранить существующие REST/WebSocket URL и персональные снимки состояния; WebSocket передаёт канонический веб-ID только после серверной проверки guest UUID.
- Обновить `ConnectionManager`: хранить несколько соединений одного пользователя, отключать конкретный сокет, а не место игрока.
- Добавить UI-действие «Покинуть лобби» и понятное состояние при истечении минутного резерва.
- Отключать кнопку голосового чата на небезопасном origin и показывать текст «голосовой чат требует HTTPS».

**Готово, когда:** веб-версия продолжает проходить текущие сценарии полного раунда и корректно переподключается в ожидании.

### T4. Перевести Telegram-бот на общий игровой сервис

**Зависимости:** T2.

- Заменить модульный `game_manager` фабрикой обработчиков, принимающей `GameCoordinator` и Telegram-уведомитель.
- Сохранить команды и inline-кнопки: создание/вход, имя, места, старт, роль, остановка, обвинение, догадка, голосование, ручный исход, отмена, выход и закрытие.
- Рендерить доменные события в Telegram DM: вход/выход, старт, остановка, начало голосования, итог и отмена.
- При действиях веб-игроков доставлять Telegram-участникам необходимые уведомления и кнопки голосования; при действиях Telegram — обновлять подключённые браузеры.
- Записывать Telegram-пользователей в статистику с `auth_provider="telegram"`.

**Готово, когда:** Telegram-хост может создать лобби, веб-игрок войти в него и завершить раунд; обратный сценарий работает так же.

### T5. Собрать единый runtime и запуск

**Зависимости:** T3, T4.

- Сделать FastAPI composition root владельцем жизненного цикла: запуск миграций/инициализации, создание координатора, запуск Telegram polling при наличии токена, корректная остановка polling.
- Без `TELEGRAM_BOT_TOKEN` запускать только веб-режим с заметным сообщением в логах.
- Обновить Makefile и README: основной запуск — единый runtime; web-only режим помечен как некроссплатформенный.
- Добавить `/healthz`, проверяющий доступность приложения и БД для Docker healthcheck.

**Готово, когда:** один локальный процесс обслуживает WebSocket-клиентов и Telegram webhook/polling с одним состоянием лобби.

### T6. Перевести persistence на миграции и PostgreSQL

**Зависимости:** T1, T2.

- Добавить `asyncpg`, Alembic-конфигурацию и базовую миграцию для `users`, `games`, `game_players`.
- Передавать `auth_provider` при создании пользователя; статистика учитывает участников обеих платформ.
- Перенести создание схемы из runtime в Alembic; тесты продолжают поднимать изолированную БД.
- Настроить `SPY_DB_URL` для PostgreSQL и документировать локальный SQLite режим.
- Не выполнять миграцию существующего локального SQLite-файла в PostgreSQL автоматически.

**Готово, когда:** чистая PostgreSQL-база поднимается командой `alembic upgrade head`, а статистика полного кроссплатформенного раунда записывается один раз.

### T7. Контейнеризировать приложение

**Зависимости:** T5, T6.

- Добавить `Dockerfile` на базе slim Python-образа: непривилегированный пользователь, установка зависимостей, запуск миграций, затем Uvicorn единого runtime.
- Добавить `.dockerignore`, исключающий виртуальные окружения, Git-метаданные, кэши, логи, локальные БД, секреты и сертификаты.
- Добавить `compose.yml` с сервисами:
  - `app`: приложение, `TELEGRAM_BOT_TOKEN`, `SPY_DB_URL`, restart policy и healthcheck;
  - `db`: PostgreSQL с healthcheck и именованным volume `postgres_data`.
- Добавить `.env.example` без секретов: токен бота, имя БД, пользователь и сильный пароль PostgreSQL.
- Опубликовать порт `8000`; отсутствие HTTPS явно указать в документации как ограничение голосового чата.

**Готово, когда:** на чистой VPS достаточно скопировать `.env`, заполнить секреты и выполнить `docker compose up -d --build`; перезапуск сервисов не теряет статистику.

### T8. Сквозная проверка и документация

**Зависимости:** T3–T7.

- Добавить интеграционные тесты с тестовым Telegram-уведомителем и WebSocket-клиентами:
  - веб создаёт → Telegram входит;
  - Telegram создаёт → веб входит;
  - обвинение, догадка и голосование инициируются с каждой платформы;
  - роли остаются персональными;
  - результат и статистика единичны.
- Добавить тесты минутного резерва места, повторного подключения, нескольких вкладок и закрытия лобби.
- Добавить Docker smoke-check: сборка образа, `docker compose config`, `/healthz` после старта.
- Обновить README: локальный запуск, Docker/VPS, переменные окружения, PostgreSQL backup, отсутствие HTTPS и будущее подключение reverse proxy.

**Готово, когда:** все unit/integration-тесты проходят, а инструкция позволяет развернуть систему без ручной настройки Python на VPS.

## Assumptions

- В первом релизе один пользователь на двух платформах — два разных игрока.
- Кроссплатформенность покрывает игровой цикл, но не чат и не голос.
- На HTTP-домене WebRTC не поддерживается; HTTPS и Caddy/Nginx — отдельная следующая задача.
- Redis, Telegram Login и миграция старых SQLite-данных не входят в этот план.
